Memory and workflows at Vooma.

AI platform engineering

At Vooma, I’m working on Vee, our AI assistant, mostly on how it remembers a conversation and picks up tasks later. I’m also building the checks around that behavior so I can work out where a response went wrong and whether a change actually helped.

Keeping the parts of a conversation that still matter

I kept recent messages in the prompt and compacted older history into shorter notes, which I could retrieve later. When someone asked Vee to get a quote and then moved on, I needed that request to remain an unfinished task rather than disappear into a general summary of the conversation.

How I kept unfinished tasks through compaction

I treated facts and tasks as different kinds of memory. A preference like “email me updates” could stay as a fact, while a quote request needed an identity and a state so a later message could refer to the same piece of work.

In this sketch, reconciliation means matching a new observation to an existing task and updating its state when there is evidence for a transition. A follow-up about a quote doesn’t by itself mean the quote arrived, so I kept the task pending until I had a reason to mark it complete.

I kept references to the source turns so I could trace a retained record back to the conversation. Compaction can omit or distort details, and those references gave me something to inspect when a memory looked wrong.

Finding the memory the user is referring to

I linked memories to the people and companies they were about so I could use those relationships during retrieval. For a follow-up about an open quote, I needed the pending task for that company, with the right access scope, even when another company had a very similar request.

Why similarity alone wasn’t enough

I used relevance to choose useful context within the eligible records, but a similar description couldn’t make a task from another company appropriate for this follow-up. I needed the access scope, entity, and pending state to remain explicit checks.

The example keeps q17’s identity through retrieval so I can explain why it was selected. q52 is still pending but belongs to another company, while q08 belongs to Northstar but is complete. I wanted both exclusions to remain visible when debugging an answer.

I still included recent conversation turns in the prompt. Retrieved memory supplied older facts and unfinished work alongside them; it didn’t replace the immediate conversation or prove that the final answer would use the context correctly.

Reusing a sequence without running everything in order

I pulled reusable workflows out of previous runs so Jev, our classifier, could pick a workflow and model for a familiar request. I kept the tool dependencies explicit, which let me run independent lookups together while holding back a call that still needed an earlier result.

What the dependency checks changed

If one lookup retrieves a company record and another retrieves a conversation, I can run them together when neither needs the other’s output. A later tool that needs a field from the company record still has to wait for that field.

In this conceptual sketch, a task becomes ready only when its required inputs are available. I still need to distinguish a valid result from a failed tool call before advancing dependent work; completing a call doesn’t automatically make its output usable.

I kept a record of the selected workflow, tool inputs, and results so I could work out whether I’d picked the wrong workflow or a particular step had failed. Reusing a procedure reduced repeated planning, but it also made choosing and checking that procedure important.

Checking whether the change fixed the right thing

I used Jev to classify response failures and moved fixes into configurable procedures that I could rerun against saved cases and simulations. If Vee asked which quote the user meant, I first checked whether the pending task reached the prompt, because changing the reply’s wording wouldn’t recover context that was missing.

How I separated a failure label from evidence of a fix

I used a failure label to narrow down what to inspect, while keeping the original conversation and retrieved context available. A label was a useful diagnosis to investigate, rather than proof that a particular procedure edit was correct.

I would keep the model settings, context, and tool-response fixtures the same when comparing the two procedures, then repeat cases where model randomness could change the result. That helps me separate the effect of the procedure edit from changes elsewhere in the run.

I reran the reported failure alongside cases that already worked, because an edit could fix one conversation and break another. Those changes affected the instructions and workflow; I wasn’t using this process to train new model weights.

I used snapshots to check a saved situation and simulations to follow the task over several turns. A reply could look sensible by itself while losing track of an unfinished request later, so I wanted evidence from both views before judging the change.

Speech and views that keep updating

I also helped fine-tune a speech model on dispatcher audio, using corrected labels and noise augmentation. Alongside that, I’m building SQL-backed artifacts that refresh an existing view as its values change, so I can update the data without regenerating the whole view through an LLM.

What I was trying to preserve in each case

For speech, I used human-corrected labels to give the model a better training target and noise augmentation to expose it to the audio conditions it needed to handle. I still needed to evaluate whether it recognized dispatcher vocabulary under those conditions, rather than judge the data work by how much audio I had collected.

For the artifacts, I separated generating the view from refreshing its values. I could use the model to help create the presentation, then rerun the SQL behind it when the underlying data changed. That gave me a more specific update path to inspect when a value looked wrong.

What I check before changing the final answer

I now follow the context through the system: whether I stored it, whether retrieval selected it, and whether it reached the prompt. I use the same approach for workflows and procedure edits, keeping the inputs and results available so I can compare what changed instead of relying on one answer that happens to look good.
