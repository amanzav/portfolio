In-car infotainment at Ford.

Embedded & systems software

I worked on in-car infotainment across two internships at Ford, with projects in connectivity debugging, hardware testing, navigation, and the tire-pressure monitoring message path. I liked being able to follow a packet through the C++ that handled it, then use the traces from a hardware run to check whether a change did what I expected.

Finding the evidence behind a firmware failure

I built a debugging assistant in Python and FastAPI over Kafka events from firmware test rigs. I scoped retrieval by rig, session, and time window so I could investigate the failed run without mixing in similar events from another one. I returned a possible explanation with the excerpts behind it, which gave an engineer something concrete to check.

I treated that answer as a hypothesis and checked the evidence bundle first when it looked wrong. If retrieval missed the lead-up to a failure, changing the wording of the explanation wouldn’t recover those events.

How I kept the explanation tied to a run

I used the rig, session, and time window together because none of them was enough on its own. A rig could have several runs, and another rig could emit a very similar reconnect failure during the same period.

For example, if I was investigating rig A in session S2, I needed the link-loss and reconnect events from that session. A timeout from A’s previous session could be relevant to a broader investigation, but I couldn’t silently use it as evidence for this particular run.

I kept the selected excerpts attached to the explanation so the engineer could inspect the same material. That also gave me a useful debugging split: I could check whether the right evidence was retrieved before deciding whether the model had interpreted it well. A citation made a claim inspectable, but it didn’t establish the root cause by itself.

Replaying faults so I could check recovery

I built a Python hardware-in-the-loop harness that replayed CAN messages against hardware and injected faults into the sequence. CAN carries messages between vehicle controllers, so I could use the harness to test what happened when messages were dropped, readings became stale, or a controller reset. I checked the return to fresh data as well as the initial failure, because detecting a fault was only part of the behavior I needed to verify.

How I separated missing messages from stale readings

I treated missing input and stale content as different cases. In one, messages stopped arriving; in the other, messages could keep arriving without carrying a fresh measurement. A pressure value staying the same could be completely valid, so I couldn’t call it stale just because two readings matched.

Moving parsing out of the interrupt

On the tire-pressure monitoring path, I reworked interrupt handling in C++ so I could capture the incoming packet and defer its parsing. An interrupt handler responds to a hardware event, so I kept that immediate path short and used event-driven dispatch to wake the processing path when work arrived. That removed the wait for a periodic poll while leaving the worker to interpret and dispatch the packet.

What I needed to check around the handoff

I had to think about the packet’s lifetime as well as where the parsing happened. If I queued a pointer into a receive buffer that was reused before the worker read it, the handoff could appear to work while parsing different bytes. I’ve used capture_owned_packet above to make that ownership requirement visible, without claiming a particular buffer implementation.

A finite queue also needs a capacity policy. As an illustrative design check, I’d ask what happens when it fills, how that condition is reported, and whether a packet is retried or discarded. I wouldn’t put a blocking wait into the interrupt just to hide that problem, and the exact response has to follow the message’s requirements.

I checked beyond the handler because shortening it didn’t account for everything a consumer experienced. Scheduling, queued work, parsing, and dispatch could still add delay, so I followed the packet through to the behavior that depended on it rather than judging the change from the interrupt alone.

Comparing routes for navigation

For navigation, I built a graph-based route ranker in C++ for the F-150 and Mustang Mach-E. I compared supplied candidate routes using an energy-oriented cost, so I could inspect why one candidate was selected under that objective. I worked on ranking that route set, and kept the selected route alongside its score when checking whether the result made sense.

What a route score could and couldn’t tell me

I could use the scoring objective to make the comparison consistent, but the winner still depended on the candidates and the assumptions behind the cost. Choosing the lowest score didn’t by itself tell me that the route set contained the best possible route.

I therefore needed to inspect the chosen route and its inputs alongside the scoring code. That was useful across the rest of my work too: I could make a decision easier to debug when I kept the evidence that produced it, whether that evidence was a route comparison, a cited trace, or a replayed message sequence.

What I took from working across both sides

I learned to follow a failure through the whole chain, from the incoming data to the behavior I could observe. I could make an individual step look better while still missing the wait or incorrect input that affected the final behavior. Keeping the traces, replay inputs, and intermediate decisions available helped me work out which part actually needed to change.
